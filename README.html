Kuno Workflow 模板说明

本仓库维护 Codex 全局规则、项目级规则模板、工作流 Skill、onboard 自动化和静态说明文档。当前主流程收敛为 Codex + GitNexus + Trellis + Chrome DevTools MCP + Playwright + Maestro，并通过 SBTD 把规格、行为、测试和领域语言串成一条可验证链路；maestro-mobile-e2e 将 Mobile / Hybrid BDD 场景固化为仓库内 Maestro flow。

SDD BDD TDD DDD Web + Mobile 验证
Trellis 任务阶段、PRD、design、implement、check、finish。
GitNexus 索引有效时做影响分析；PDG、taint、trace 和多分支查询需显式 opt-in。
Playwright CLI 负责 Web E2E 和回归，MCP 负责探索和 locator 辅助。
Maestro 负责 Android、iOS、RN、Flutter、Hybrid App E2E；flow 资产落到 maestro/flow。

Workflow

当前模板主线

模板以项目事实为优先级，只有在存在强证据时才启用可选工具。普通修改保持最小、可验证、可回滚；复杂任务通过 Trellis 和相关 Skill 管理阶段、文档和验证。

1. 需求读取规则、lessons、项目文档，必要时澄清。
2. SBTD规格、行为、测试、领域语言对齐。
3. 影响GitNexus 可用时做影响分析。
4. 实现按项目规范和 Skill 边界改动。
5. 验证项目测试、BDD、Web、Mobile。
6. 风险发布就绪、Channel preflight、剩余风险。
7. 同步仅在用户输入 sync / 同步时写入本地生效路径。
AGENTS
常驻路由、触发条件、硬性安全边界和最终报告要求。
Skills
详细流程、命令参数、检查清单和专项判断按场景延迟加载。

SBTD

四个驱动开发概念

SBTD 是本模板对 SDD、BDD、TDD、DDD 的组合简称。它不是新框架，而是用于约束 Codex 工作流的协作顺序：先明确意图和语言，再固化可观察行为，最后用测试推动实现和回归。

SDD

Specification-Driven Development。用 PRD、design、implement、验收标准和长期规则说明要做什么、为什么做、怎么验证。

BDD

Behavior-Driven Development。用户可见行为默认需要持久场景，优先使用 Given / When / Then 和项目已有 Gherkin 约定。

TDD

Test-Driven Development。适用于 bug 修复、核心逻辑、高风险改动和回归敏感路径，用红测、绿码、重构推进。

DDD

Domain-Driven Design。通过统一语言、bounded context、CONTEXT 和 ADR 降低业务术语和模型边界的不确定性。

Boundaries

工具职责边界

Chrome DevTools MCP、Playwright CLI、Playwright MCP、Maestro CLI、Maestro MCP 和 web-ui-autotest-generator 不互相替代。模板要求在最终输出中显式报告相关状态，避免把诊断、探索和可重复测试混在一起。

工具 主责 边界
Chrome DevTools MCP 真实 Chrome 中的 console、network、storage、performance trace、screenshot 诊断。 提供现场证据，不作为 CI 或 E2E 通过依据。
Playwright CLI 项目内 Web E2E、Web 回归和 CI gate。 需要项目级安装；缺失时先询问用户，拒绝后只可降级为诊断。
Playwright MCP Agentic Web 探索、可访问性快照、locator 辅助。 不替代 playwright test。
Maestro CLI Android、iOS、React Native、Flutter、Hybrid App E2E 和可选 Web smoke。 Web 只适合 smoke，不作为 Web 回归主责。
Maestro MCP 设备检查、view hierarchy、截图和 flow 辅助。 依赖 Java 17+ 和 Maestro CLI；MCP 缺失但 CLI 可用时继续 maestro test。
web-ui-autotest-generator 生成和审计 repo-resident Playwright 测试资产、选择器和覆盖率。 执行底座仍是项目内 Playwright CLI。
maestro-mobile-e2e 从 BDD 场景生成和维护 repo-resident Maestro Mobile / Hybrid flow，并约束报告路径。 不替代 BDD、项目验证或 Maestro CLI。

Validation

最终验证工具栈

最终验证按风险从项目原生命令开始，再叠加 BDD、Web、Mobile 和发布就绪检查。无法执行时必须说明尝试命令、失败原因、替代检查和剩余风险。

项目原生验证

优先运行项目级 AGENTS、README、package scripts、Makefile 或 CI 中定义的 lint、typecheck、static analysis、unit、integration、build；覆盖 Node、Python、Go、Dart、Java、Kotlin、C++、Swift 和 Objective-C。

行为和测试追踪

用户可见行为检查 BDD 场景和测试追踪；高风险逻辑优先使用 TDD 固化回归。

Web 验证

Chrome DevTools MCP 诊断现场问题，Playwright CLI 执行可重复 Web 回归，Playwright MCP 辅助探索。

Mobile 验证

Java 17+ 通过后使用 Maestro CLI 执行移动 flow；需要设备级资产时由 maestro-mobile-e2e 从 BDD 生成 maestro/flow/*.yml。

测试资产

只有需要把 Web UI 回归固化进仓库时，才调用 web-ui-autotest-generator。

发布风险

生产路径、外部集成和部署敏感变更进入 release-readiness；高风险 review 可做 Channel preflight。

Mobile E2E Contract

Maestro flow 和报告路径

Mobile / Hybrid BDD 场景需要设备级覆盖时，使用 maestro-mobile-e2e 生成或维护 Maestro flow。Flow 是可入库测试资产；Maestro CLI 运行报告是本地/CI 产物。

Flow Assets
maestro/flow/<english-scenario>.yml，文件名 lower-kebab-case，YAML name 使用英文业务场景名。
Smoke
全量回归 / smoke flow 固定为 maestro/flow/smoke.yml。
JUnit
.maestro/reports/maestro-report-{flow_name}-{YYYY_mm_dd}-{HH_MM_SS}.xml
HTML
.maestro/reports/maestro-report-{flow_name}-{YYYY_mm_dd}-{HH_MM_SS}.html

Maestro 官方默认运行 artifacts 位于用户 home 下的 ~/.maestro/tests，不是仓库内测试资产。iOS 真机 driver、transport、view hierarchy 或 tap crash 问题由 maestro-mobile-e2e 按标签 / 关键字懒加载对应 lesson。

Install Gates

检测、安装和 fallback

模板不默认假设工具存在。CLI 或 MCP 缺失时，先按证据检测，再根据用户确认安装或降级；降级不能冒充完整验证。

Playwright CLI
检测 package.json、Playwright 配置、E2E 目录和脚本。需要 Web 回归但缺失时询问是否安装到项目 devDependency。
Playwright MCP
只作为 MCP 可见性检查和探索能力；不可见时不阻塞 Playwright CLI。
Java 17+
Maestro 前先运行 java --version，失败再用 java -version。默认引导安装 OpenJDK Temurin 21 最新 JDK；用户指定版本必须大于等于 17。
Maestro CLI / MCP
Java 通过后检查 CLI，CLI 可用后再检查 MCP。MCP 缺失但 CLI 可用时继续 maestro test。
Chrome DevTools MCP
由 Agent 或 IDE 配置提供，只负责诊断和证据收集。
状态报告
最终输出要列明各工具是 run、blocked、skipped、not-needed、available、installed 或对应模板状态。

Repository

源文件和同步规则

本仓库是配置摘录和模板源，不是真实业务项目。普通修改只更新仓库源文件；只有用户输入 sync 或 同步 时，才同步允许列表中的全局规则和 Skill 到本地生效路径；Skill 必须按目录整体同步，包含 kuno-workflow-onboard-skills/ 自身。

Maintenance

README 同步规范

后续任何模板内容更新，如果影响工作流、工具职责、安装检测、SBTD、验证策略、忽略规则、同步流程或用户可见路径，必须同时评估并更新 README.md 和 README.html。如果判断无需更新，最终输出要说明原因。

当前文档与仓库模板源对齐：SBTD 负责开发方法，Chrome DevTools MCP / Playwright / Maestro 负责分层验证，web-ui-autotest-generator 和 maestro-mobile-e2e 只在需要沉淀对应 E2E 测试资产时启用。
