Global Rules

全局模板负责“默认怎么做”

它定义 Agent 的默认工程纪律，但明确让位于当前项目已有规范、测试、配置和工作流。

优先级

  • 更深层 AGENTS.md 优先。
  • 项目文件和工具输出优先。
  • 不假设可选工具一定可用。

命令执行

  • 优先使用 rtk 前缀。
  • rtk 不可用时回退原生命令。
  • 不因 wrapper 不可用中止任务。

验证最低要求

  • 修改代码后必须验证。
  • 优先项目定义命令。
  • 无法执行时说明原因、替代检查和风险。
全局规则的目标不是增加流程负担，而是保证每次修改都能解释清楚：依据是什么、改了什么、怎么验证、风险在哪里。
适用对象：所有继承该模板的代码仓库。Slide 05
Project Rules

它把全局默认约束落到真实项目：事实源、工具证据、目录提交策略、验证命令和长期 lessons。

当前项目的代码、配置、测试、README、CI、任务产物和工具输出优先于通用假设。

Tool Matrix

工具不是全开，而是按证据启用

模板的核心是避免“因为工具存在就使用”。每个工具都有启用条件、跳过条件和输出责任。

工具主要用途启用条件跳过条件
Trellis任务生命周期、workflow、task artifacts。存在 .trellis/、workflow、命令或项目规则声明。没有强证据时不启用。
GitNexus影响分析、变更检测、探索辅助。MCP 可用且当前项目已有索引。MCP 不可用或没有项目索引。
TestSprite测试计划、UI/E2E、API 和回归验证辅助。涉及端到端流程、UI、API 集成、测试计划或回归验证。无需 E2E 或 MCP/环境未配置时。
Skills场景化执行规范。任务明确匹配 Skill 描述。不匹配、不可用或弱关联时。
工具输出只能辅助判断，不能替代源码、项目文档、测试和实际 diff。Slide 07
TestSprite

TestSprite 负责测试计划、E2E 和回归验证辅助

在模板编排中，它通常位于编码后验证阶段，尤其适合 UI、端到端业务流程、API 集成和回归检查。

01
理解需求
读取 PRD 或从代码推导标准化 PRD。
02
生成计划
生成 frontend 或 backend test plan。
03
执行测试
生成可执行测试并在环境中运行。
04
反馈修复
输出结果、日志、报告和修复建议。
TestSprite 不是普通单元测试的替代品。项目自己的 lint、test、build 仍然是基础验证；TestSprite 用于补充端到端和回归视角。
官方文档强调通过 MCP server 与 IDE/Agent 集成。Slide 08
TestSprite Setup

TestSprite 的典型 MCP 配置流程

实际配置依 IDE 而异，但核心步骤一致：账号、API Key、Node、MCP server、本地应用和测试范围。

1

账号与 Key

注册 TestSprite，创建 API Key，按团队密钥策略保存。

2

运行环境

确认 Node.js 版本满足 MCP server 要求。

3

IDE MCP

在 Cursor、Claude Code、VS Code 等配置 MCP server。

4

本地服务

启动 frontend dev server 或 backend API，并确认端口。

5

测试范围

选择 frontend/backend，codebase/diff，是否需要登录。

6

执行与报告

生成计划、运行测试、查看报告并回传修复建议。

凭据不应硬编码进测试文件或仓库。Slide 09

Trellis Evidence

只有存在强证据时，才进入 Trellis

模板把 Trellis 视为项目生命周期工具，而不是默认所有仓库都必须启用的组件。

强证据

  • 存在 .trellis/。
  • 存在 .trellis/workflow.md。
  • 存在 $trellis-* 命令。
  • 项目规则明确说明使用 Trellis。

最低禁令

  • 未读 workflow 不改变任务状态。
  • 未读相关 spec 不改长期规则。
  • 不绕过 workflow 或手动跳 phase。
  • 不把一次性计划写入 spec。
一旦 Trellis 可用，实际生效的依据是项目中的 .trellis/workflow.md，不是模板中的抽象描述。
复杂度决定是否进入 planning，协作形态决定是否启用 Channel。Slide 14
Trellis Workflow

native 是默认标准 workflow

native 以 Trellis 阶段、任务产物和项目验证为中心，不强制所有修改都测试先行。

1

读取事实

读取 workflow、spec、prd/design/implement。

2

before-dev

执行 $trellis-before-dev，确认可以开始实现。

3

实现与验证

按任务产物实现，运行项目验证命令。

4

check / finish

执行 $trellis-check，验证通过后 $trellis-finish-work。

native 不禁止 tdd Skill。bug 修复、核心业务逻辑、算法、数据同步、导入导出或高风险修改，仍可按需使用测试先行。
简单文案、样式、配置说明或纯文档修改不强制 TDD。Slide 15
Trellis TDD

tdd workflow 是生命周期编排，不等于 tdd Skill

两者可以组合，但不能互相替代：Trellis 管阶段，Skill 管具体测试先行方法。

Trellis tdd workflow

  • 按 .trellis/workflow.md 执行阶段。
  • 开发前仍执行 $trellis-before-dev。
  • 开发后仍执行 $trellis-check。
  • 验证通过后才 $trellis-finish-work。

tdd Skill

  • 用于具体 red-green-refactor。
  • 先写失败测试，再实现最小代码。
  • 重构时保持测试通过。
  • 适合复杂逻辑和高风险行为。
仅用户明确要求 TDD 或项目已采用测试驱动流程时切换到 tdd workflow。Slide 16

Trellis Channel

Channel 是显式协作运行时，不是普通 Trellis 默认入口

只有用户明确要求多 Agent、多模型、worker、forum、thread、并行评审或外部 orchestrator 协作时才启用。

不要因为这些原因启用

  • 任务复杂或文件多。
  • 普通 bug 修复。
  • 常规重构或添加测试。
  • 普通 Trellis 任务。

可以启用的场景

  • 用户要求多 Agent 协作。
  • 需要 worker 并行评审。
  • 需要 forum / thread 讨论。
  • 需要外部 orchestrator。

使用后必须整理

  • 说明 channel 和 worker。
  • 整理结论到 task artifacts 或 spec。
  • 说明是否有未清理 worker。
  • runtime 默认不提交。
Channel 不替代 before-dev、check 或 finish-work。Slide 18
Validation

project-validation 负责修改后的验证策略

模板要求优先使用项目已有命令，只有缺少项目定义时才按语言生态回退。

Node / JS / TS

rtk npm run lint
rtk npm run test
rtk npm run build

涉及类型、DTO、API 返回值、组件 props、状态结构时补 typecheck。

Python

rtk ruff check .
rtk ruff format .
rtk ty check .
rtk pytest

按修改范围选择格式、类型和业务测试。

Go

rtk go test ./...
gofmt
go vet ./...

仅依赖变化时运行 go mod tidy。

无法执行完整验证时，必须说明尝试命令、失败原因、替代检查和剩余风险。Slide 19
Lessons

lesson 是长期经验，不是普通过程日志

只有出现长期复用价值的错误、修复或流程偏差时才记录，避免把临时噪音写进项目长期文档。

必须考虑记录的场景

  • bug 修复或回滚。
  • 工具判断错误或验证失败。
  • Trellis 阶段错误。
  • GitNexus 影响分析不匹配。
  • Channel / worker 上下文丢失。

推荐格式

## <简短标题>

- 问题：
- 根因：
- 修复：
- 预防：

优先记录到项目可审查位置，例如 .trellis/spec/lessons.md、docs/lessons.md 或 .codex/lessons.md。

普通任务总结不等于 lesson。Slide 20

Adoption Checklist

给其他仓库落地前的检查清单

目标不是把所有工具都装上，而是让项目拥有清晰的事实源、可验证的流程和明确的工具边界。

规则模板

  • 项目根目录有清晰的 Agent 规则。
  • 项目事实源和验证命令已补充。
  • 目录提交策略符合团队需求。

工具配置

  • Trellis 只有强证据时启用。
  • GitNexus 只有索引存在时启用。
  • TestSprite 只在测试场景需要时启用。

执行闭环

  • 修改前知道读取哪些产物。
  • 修改后知道跑哪些验证。
  • 失败和跳过检查必须说明风险。
  • 长期经验才记录 lesson。
最终标准：可理解、可验证、可维护、可回滚。Slide 23
